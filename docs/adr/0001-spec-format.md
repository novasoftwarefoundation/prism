# 0001: Spec format: Elixir DSL for tokens and components, generated per platform

Status: proposed, 2026-10-31

## Context

Prism is a look for scientific software: a Tailwind preset plus component CSS, published as `@novasoftwarefoundation/prism`. Native apps need the same look: iOS now, Android later. Today a native app copies the values by hand, and the web's component CSS doesn't use the preset's own tokens, so values drift between platforms and even within the web package.

The fix is one spec with a generator per platform, and the generated code committed so every change is reviewable. The source of truth is prism 0.1.7's styling: `tailwind.preset.js`, `css/base.css` and `css/components.css`. The first spec must reproduce it, so nothing changes for existing consumers.

## Decision

"The spec" is the whole; it has these layers:

| Layer | What | Where |
|---|---|---|
| Schema | The DSL and its rules: what a valid spec is | `Prism.Schema` |
| Tokens | Colors, shadows, text shadows, spacing, sizes, radii, font families and faces, font styles, text sizes | `Prism.Tokens` (`__schema__/0` returns it as data) |
| Components | Components with a base style, parts, variants and states, built from tokens | `Prism.Components` (later) |
| Generated code | Web (Tailwind preset and CSS), Swift, later Kotlin | this repo: the root (web), `swift/`, `kotlin/` (later) |

The first step has the schema's token part, the tokens and the web generator for `tailwind.preset.js` and `css/base.css`. `css/components.css` stays hand-written until the components are in the spec.

1. **Tokens are declared, not computed.**

   ```elixir
   group "Brand colors" do
     color :primary, "#4272EF"
   end
   color :delete, :error                      # alias: same value, its own name
   shadow :prism_card, y: 5, blur: 20, color: {:black, 0.1}
   shadow :floating, :prism_card, deprecated: true
   font :button, :nunito_sans, 700            # web: font-button
   text :button, 18, 18                       # web: text-button
   radius :default, {0.25, :rem}
   ```

   Font styles (family and weight) and text sizes (size and line height) stay two lists, because 0.1.7 has two different key sets for `font-…` and `text-…`. A platform that wants one type style combines a font and a size by name.

2. **Components hold design values only** (later).

   ```elixir
   defcomponent :button do
     style font: :button, text: :button, radius: :default, transition: {150, :ease_in_out}
     variant :primary, background: :primary, foreground: :white, padding: [y: 15, x: 16] do
       state :pressed, padding: [top: 16, bottom: 14], shadow: :prism_btn_pressed
       state :disabled, opacity: 0.5
     end
   end
   ```

   - The properties are a fixed, typed list: colors, lengths, insets, radius, font, text, weight, shadow, opacity, motion, decoration.
   - A value is a token reference or a literal. Colors are `:token`, `{:token, alpha}` or `"#RRGGBB"`. Lengths are px (points on iOS, dp on Android), `{n, :rem}` or `{n, :percent}`.
   - CSS mechanics are not in the spec: `display`, `cursor`, `appearance`, focus outlines, keyframes, the spinner's `filter`, the checkbox SVG. They live in the web generator's templates, just as native views live in native code.

3. **Mistakes fail at compile time and point at their line:**
   - an unknown option, property or token kind;
   - a name that isn't a snake_case atom;
   - a duplicate;
   - a value of the wrong type (a lower-case hex color, a weight outside 100..1000);
   - a reference to a missing token, or one of the wrong kind;
   - a `state` outside a component, or a node in the wrong place (with components).

4. **Naming:**
   - Spec names are snake_case atoms.
   - Web keys replace `_` with `-` (`prism_btn_pressed` → `prism-btn-pressed`).
   - Swift uses camelCase (`Prism.Shadows.prismBtnPressed`) and escapes keywords.
   - CSS class names of components (`prism-btn-…`, `prism-radio-label`) live in the web templates, because 0.1.7's names don't follow one rule.

5. **Generators read `__schema__/0`, never the source.** They are Mix tasks named `mix prism.gen.<target>`. Each generated file starts with a `Generated by prism (mix prism.gen.<target>)` line, and a generator never overwrites a file without that line (`Prism.Gen.write!`).
   - Web (`mix prism.gen.web`): EEx templates that splice in spec values. The templates hold the web mechanics; every design value comes from the spec.
   - Swift (later): one file with value types, the tokens, and one resolved style per component, part, variant and state. Values only; views stay hand-written.
   - Kotlin (later): the same values for Compose.

6. **The generated files are committed.** CI regenerates them on every pull request and fails when they differ from what is committed. Reviewers see every output change; SwiftPM needs the Swift source at the tag.

7. **Brand-neutrality and theming:** the spec holds Prism's defaults. The first spec keeps 0.1.7's behaviour: the preset is overridable, the component CSS is not. Emitting CSS custom properties for theming is a possible later change, not part of this decision.

8. **One version for everything.** `mix.exs` has the same version as `package.json`. A release tag `vX.Y.Z` will be the npm version and the SwiftPM version. 0.x rules apply: a removed token, class or variant is a minor bump.

9. **Byte-compatibility with 0.1.7.** The web generator spells values the way 0.1.7 does in each file:
   - upper-case hex in the preset;
   - two-decimal alphas in the preset (`0.10`);
   - `0px` in base.css's text shadows, `0` in the preset's shadows;
   - prettier's 80-column wrap in `@font-face` rules.

   `test/golden/0.1.7/` holds 0.1.7's files, and a test requires the generated output to differ from them only by the header line and the reviewed diff in `test/golden/0.1.7.diff`. Today that diff is one line: the deprecated `floating` shadow is an alias of `prism-card`, so it is written `0 5px 20px 0` instead of `0px 5px 20px 0px`, the same computed value. Any other change to the output fails the test until the diff file is updated, so it shows in review.

## Alternatives

| Option | Why not |
|---|---|
| Style Dictionary / W3C design-token JSON | The standard for tokens, but it has no components with variants and states, needs a Node toolchain next to Elixir, and the generators would fight its transforms to reproduce 0.1.7 byte for byte. A later generator can export design-token JSON from `__schema__/0` for tools that need it. |
| Keep the CSS as the source and parse it for native platforms | It makes the CSS mechanics the contract, and there is still no place for the values the CSS hard-codes. |
| Tokens only, components hand-written per platform | That is today's drift. Components are where platforms most need the same numbers. |
| A data file (`.exs` maps) instead of macros | Simpler, but no compile-time errors with line numbers. |

## Consequences

- One language and one review for every platform's styling. Native apps get the same numbers as the web by construction.
- Editing the look means editing Elixir and running `mix prism.gen.web`. A docs generator can later turn the spec into the README's token tables.
- The web templates still look like CSS and JavaScript. Reviewers see web mechanics there and design values in the spec.
- 0.1.7's inconsistencies stay until someone changes them on purpose, each in its own pull request with a visible golden diff.
